# #393 readout: pull frequency + usefulness, 13-day post-redeploy window

Run date: 2026-08-03. Window: 2026-07-21 to 2026-08-03 (`--days=13`, `--limit=120`).
Harness: `scripts/eval/pull-usefulness.ts`. Judge: `qwen3.5:4b` on local Ollama (the
locked judge; pulled fresh for this run, it was absent from the host).
Raw output: `2026-08-03-393-readout.json`.

This is the deferred re-measure filed 2026-07-03 at the #392 pull-first ship. Its
first two windows were void: the 07-04 window was contaminated by the 2026-07-08
NxtOS install silently downgrading production to 0.20.0 (reverting U1
conversation_id logging and killing the embedder lane), and the window restarted
2026-07-21 on redeploy. This is the first clean measurement.

## Result vs the 2026-07-03 baseline

| Metric | Baseline (07-03) | This window (08-03) | Delta |
|---|---|---|---|
| usefulness@pull | 72.4% (n=78) | **79.4%** (n=80) | +7.0pp |
| Off-topic | 21.8% | **13.8%** | -8.0pp |
| Session pulls | 66.7% | **77.3%** | +10.6pp |
| Fact pulls | 88.1% | **87.5%** | -0.6pp |
| Join rate | 40.0% (78/195) | **81.6%** (80/98) | +41.6pp |
| Raw MCP pulls seen | 3,920 | 5,866 | +1,946 |

Verdicts this window: 58 used / 11 partial / 11 unused.

**Both pre-registered targets met.** The target was usefulness@pull >= 60%; the
result is 79.4%. The frequency target was pulls/day up from 3.5; see below.

**The +7.0pp usefulness gain is not statistically significant** (SE 6.8pp, z=1.03).
Read it as "held well above target and did not regress," not as a proven
improvement. The honest claim is stability at a high level across five weeks and a
deployment regression, on independent samples of comparable size.

## Frequency

Measured directly from `~/.nlm/query_log.jsonl` over the same window, since the
harness reports totals rather than a per-day rate.

- 159 MCP pulls across 12 active days after the pre-registered strip set.
- 84 of those are a repeated `NLM` query (`limit: 1`, `runtime: null`, always
  returning `ws_1`) — automated lookup traffic, not agent pulls. See the caveat
  below.
- Excluding it: **75 genuine pulls / 12 active days = 6.3 per active day**, against
  the 4.2 pre-ship baseline and the 3.5/day target. Up roughly 49%.

Distribution is bursty rather than steady: two heavy days (07-22 tenancy work,
08-03) carry a disproportionate share, with a median day near 6. The 08-03 figure
includes the agent session that produced this readout and is not representative of
normal operator use.

## The join-rate result is the real finding

Join rate went 40.0% to 81.6%. That is the U1 conversation_id work landing: at
baseline, six of every ten genuine pulls could not be traced to the response that
followed them and were simply unscoreable. The instrument now sees twice as much of
what it is trying to measure. Every other number in this readout rests on a
sample that is qualitatively better attributed than the baseline's, which is a
second reason to treat the +7.0pp as soft.

## Caveats

1. **The strip set is stale.** `PROBE_EXACT_QUERIES` covers `pgvector`, `hono`,
   `x`, and empty. It does not cover the `NLM`/`limit: 1`/`ws_1` automation, which
   first appeared 2026-07-03 at 14:31 UTC — after the baseline run at 10:07, so the
   baseline never saw it. The harness's dedup pass absorbs most of the volume
   (98 genuine, not 159), and the rows carry no `conversation_id` so they land in
   `unjoinable` rather than being scored. Usefulness is therefore uncontaminated,
   but the genuine-pull denominator and the frequency count both need it excluded
   by hand until the strip set is updated. Expanding the strip set requires
   re-establishing the baseline first, per the lock recorded in `probe-filter.ts`.
2. **Single-runtime sample.** Only `claude-code` appears. pi.dev and Hermes Agent
   still run per-prompt ambient injection and emit no MCP pulls, so the per-runtime
   split #393 asked for cannot be produced from this window.
3. **Judge freshly installed.** `qwen3.5:4b` was absent from the host and pulled
   for this run. Same tag as the locked judge, so the comparison holds, but this is
   a different physical model instance than the one that produced the baseline.

## What this unblocks

The one-parameter hybrid tiebreaker fix from #394 was gated on "no second
intervention inside the #393 window." That window is now closed with a clean
readout, so the gate lifts. The fix remains unlanded as of this date:
`recall-service.ts` still passes `queryTokens` into `finalize` only on the keyword
leg, so hybrid still forgoes the metadata tiebreaker and carries the ~14pp drag
measured at the 2026-07-06 private-bench run.
